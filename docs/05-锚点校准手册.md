# 05 · M0 锚点校准手册

> 版本 v0.1 · 2026-11-08
> 适用：`kiseki_runtime` M0 的**实机界面锚点校准**，以 **崩坏：星穹铁道 4.6.0**（2560×1600 全屏、DPI 120%）为样本。
> 配套：[configs/hsr.yaml](../configs/hsr.yaml) · [锚点证据图](anchors/hsr/README.md) · [scripts/anchor_snips.py](../scripts/anchor_snips.py) · [04-DSH集成与运行时方案](04-DSH集成与运行时方案.md)
>
> 本文记录的是 2026-11-08 夜间在真机上跑通的流程，不是设计稿；坐标、路径和坑都来自实机结果。

## 0. 锚点是什么

M0 还没有视觉识别，`game_act` 只接受两类目标：

1. **profile 里声明的锚点**（`target: {anchor: <id>}`）；
2. **0–1 归一化坐标**（`target: {x: 0.683, y: 0.527}`）。

绝对屏幕像素、任意脚本都会被 runtime 拒绝。每个锚点写在 `configs/<game>.yaml` 的 `ui.anchors` 下：

```yaml
- id: phone_mail
  template: null          # M0 不用模板；M1 模板匹配的入口
  region: [0.657, 0.493, 0.709, 0.561]   # [x0, y0, x1, y1]，相对窗口客户区归一化
  threshold: 0.85         # 预留给 M1 的模板匹配阈值
  note: 手机 UI「短信」图标（四列网格，2026-11-08 实机逐格校准）
```

要点：

- `region` 是 **`[x0, y0, x1, y1]` 的矩形**，不是 `[x, y, width, height]`；`y` 轴向下。
- 坐标相对**窗口客户区**（不含标题栏/边框），不是整个屏幕。
- M0 的点击取 `region` 的**中心点**：`((x0+x1)/2, (y0+y1)/2)`。
- `region` 同时也是证据图的裁剪框；`scripts/anchor_snips.py` 会按它裁图。
- `template: null` 时 `threshold` 不参与判定，但保留字段，避免 M1 接入模板时改协议。

## 1. 为什么锚点必须实机校准

归一化坐标只能消除「整体等比缩放」，消除不了下面四类变化：

| 变化 | 会发生什么 | 例子 |
|---|---|---|
| 分辨率 / 宽高比 | 边缘锚定的 UI 有固定像素 padding，归一化位置会漂移；16:10 与 16:9 的布局不同 | 1280×720 与 2560×1600 下，右上角图标的 x 不一样 |
| DPI 缩放 | 系统缩放 100% / 120% / 150% 会改变窗口客户区的像素尺寸与 DWM 合成方式；未开 DPI awareness 的工具拿到的矩形也不同 | 本机 120%，runtime 用 `enable_dpi_awareness()` 后才稳定拿到 2560×1600 客户区 |
| 游戏 UI 版本 | 图标位置、数量、面板结构随版本变化；旧锚点可能落在空白处 | 4.6.0 的手机 UI 是四列网格；右上角最左侧图标**不是**手机入口 |
| 窗口模式 | 无边框全屏、独占全屏、窗口化三种模式的客户区尺寸和截图方式不同 | 桌面全屏时窗口 DC 会抓到旧帧，必须走屏幕 DC 裁剪 |

所以校准的触发条件是：**换游戏版本、换分辨率、换 DPI、换窗口模式、UI 布局明显变化**。改完必须重记 `note`（日期、游戏版本、分辨率、DPI、界面状态），并重新生成证据图。

不要相信占位坐标。夜间校准时 `hud_phone` 就曾按「手机入口」写入，实测点它没有反应（疑似公告/活动入口），手机菜单实际是 `Esc` 打开的。

## 2. 校准前准备

### 2.1 清空代理环境变量后再启动游戏

DSH 的 `<HOME>\.dsh\.env` 会把 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 注入子进程。本机曾指向 `127.0.0.1:7897`，但代理并没有运行，星铁启动后会直接报 **「网络连接错误」**，根本到不了标题画面，也就无法校准。

启动前在干净的 shell 里清掉大小写共 6 个变量，再 `Start-Process`：

```powershell
$env:HTTP_PROXY="";  $env:HTTPS_PROXY="";  $env:ALL_PROXY=""
$env:http_proxy="";  $env:https_proxy="";  $env:all_proxy=""

Start-Process "C:\miHoYo Launcher\games\Star Rail Game\StarRail.exe"
```

- 星铁直接启动 exe 即可，约 40 s 到标题画面；点标题底部「点击进入」后自动登录，黑屏加载约 30 s 进入派对车厢。
- 终末地相反：直接启动 `Endfield.exe` 会弹「请通过官方启动器打开游戏」，必须经鹰角启动器 `C:\Hypergryph Launcher\launcher.exe` 进入。
- 如果 DSH 长期带死代理启动，应在 `.env` 里注释对应行（夜间已备份为 `.env.bak-kiseki-20261108`），或由启动脚本探测并清空代理。

### 2.2 确认窗口与采集后端

按顺序确认三件事，任何一步不成立都先修，不要继续写锚点：

1. **profile 加载正常**：`game_profiles` 返回 `profiles` 包含目标游戏，`errors` 为空。YAML 解析失败时 runtime 不会崩，但该 profile 会缺失，错误会列在 `errors` 里。
2. **窗口已聚焦**：`game_focus <game_id>` 返回 `window.hwnd`、`client`（本机为 `2560x1600`，同一份数据也在 `window.client`）、`window.dpi`（`120`）、`foreground: true`。`foreground: false` 说明窗口没被抬到前台，后续输入会被前台校验拒绝。
3. **采集后端正确**：`game_capture <game_id>` 返回 `backend`，取值有：

   | backend | 含义 | 适用 |
   |---|---|---|
   | `screen` | 抓主屏再按客户区裁剪 | 前台全屏 / 无边框 D3D 游戏（**本机星铁应为此值**） |
   | `printwindow` | 让窗口自己渲染（`PW_RENDERFULLCONTENT`） | 后台窗口 |
   | `window-dc` | 直接 BitBlt 窗口 DC | 前两者都失败时的兜底 |

   全屏 D3D 的 flip 模型不会更新窗口 DC，所以窗口 DC 截图会拿到旧帧；runtime 在前台时优先走 `screen`。profile 里的 `capture.backend: gdi` 是声明配置，M0 实际采集路径由窗口是否在前台决定，以 `game_capture` 返回的 `backend` 为准。

采集结果同时返回 `foreground` 与 `notice`。若 `foreground: false`，`notice` 会提示画面可能过期或被遮挡。拿到 PNG 后必须用 `read_image` 看一眼：全黑、旧帧或被遮挡都不算数，先解决前台/锁屏/电源问题再校准。

runtime 在 `game_focus` / `game_capture` / `game_act` 时会调用 `SetThreadExecutionState` 保持屏幕常亮，`game_stop` 时释放；锁屏或系统休眠会让 GDI 截图变黑。

## 3. 标准校准流程（以 hsr 为例）

### 第 1 步：聚焦并确认基线

```text
game_focus("hsr")
→ hwnd 989554, client 2560x1600, dpi 120, foreground true
```

同时记录当前 **游戏版本、分辨率、DPI、界面状态**，后面要写进锚点 `note`。

### 第 2 步：截全屏

```text
game_capture("hsr", label="calib-title")
→ captures/<stamp>-hsr-calib-title-xxxxxx.png
  width 2560, height 1600, backend screen, foreground true
```

`region` 不传即整窗（`[0, 0, 1, 1]`）。需要细看某个区域时可以传归一化 `region` 再截一张，但校准锚点应以整窗截图为基准，避免二次缩放误差。

### 第 3 步：按归一化坐标估算区域

在截图上量出目标图标的像素矩形 `[left, top, right, bottom]`，换算成归一化区域：

```text
x0 = left  / width      y0 = top    / height
x1 = right / width      y1 = bottom / height
```

例：短信图标在 2560×1600 截图上约为 `[1682, 789] – [1815, 898]`，则：

```text
x0 = 1682/2560 ≈ 0.657    y0 = 789/1600 ≈ 0.493
x1 = 1815/2560 ≈ 0.709    y1 = 898/1600 ≈ 0.561
region = [0.657, 0.493, 0.709, 0.561]
中心 = (0.683, 0.527) → 屏幕像素 (1748, 843)
```

实用规则：

- 区域要**完整包住图标并留一点边**，不要贴边裁；中心点必须落在可点击区域里。
- 归一化保留 3 位小数即可，1 px 误差在 2560 宽下约 0.0004。
- 先算中心、再向四周扩成矩形，可以避免 `[x, y, w, h]` 的顺序错误。
- 同一排/列的图标先用一个实测值，再按步长推其余位置，最后逐格截图复核。

### 第 4 步：写入 `configs/<game>.yaml`

在 `ui.anchors` 列表里追加条目，`id` 用小写加下划线，按界面分组（`title_*` / `hud_*` / `phone_*` / `map_*`）：

```yaml
- id: phone_mail
  template: null
  region: [0.657, 0.493, 0.709, 0.561]
  threshold: 0.85
  note: 手机 UI「短信」图标（四列网格，2026-11-08 实机逐格校准）
```

注意：

- `id` 必须唯一，且被 `game_act` / `game_skill` / 证据脚本引用；改 id 要同步改引用。
- 文件必须放在 runtime 实际加载的 `configs/` 目录（`game_profiles.profiles_dir`），否则改了也不生效。
- 保持 YAML 缩进正确；`region` 用 `[x0, y0, x1, y1]`。

### 第 5 步：先用 `dry_run` 验证计划

`game_act` 默认继承 profile 的 `safety.dry_run: true`，只返回「将会点哪里」，不注入输入：

```json
game_act("hsr", [{"type": "click", "target": {"anchor": "phone_mail"}}], dry_run=true)
→ planned[0] = {
    "kind": "click",
    "target": "anchor:phone_mail",
    "normalized": [0.683, 0.527],
    "screen": [1748, 843],
    ...
  }
```

检查 `screen` 是否落在目标图标上、是否与截图估算一致。偏了就改 `region`，不要靠「多点几次」碰运气。

### 第 6 步：真实点击验证

确认 `foreground: true` 后，显式传 `dry_run: false` 只执行**一个**动作：

```json
game_act("hsr", [{"type": "click", "target": {"anchor": "phone_mail"}}], dry_run=false)
→ executed[0] = { ..., "screen": [1748, 843] }
```

然后立刻 `game_capture` 截图确认界面变化。夜间实测：

- `phone_mail` → 打开「短信」联系人列表；
- `map_close` → 点击 `[2473, 77]` 关闭地图回到车厢；
- `title_enter` → 点击中心 `(0.5, 0.945)` 从标题进入游戏。

一次只验证一个锚点；点击可能已经生效，不要盲目重试。验证期间保持 profile 的 `safety.dry_run: true`，只在单次调用里覆盖。

### 第 7 步：用 `scripts/anchor_snips.py` 生成证据图

```powershell
python scripts/anchor_snips.py
```

脚本会（需要 Pillow，仅开发依赖）：

1. `game_focus("hsr")`；
2. 连按 3 次 `close_panel` 回到主界面，截 `ingame`；
3. 用 `phone_open`（`Esc`）打开手机，截 `phone`；
4. 用 `m` 打开地图，截 `map`；
5. 按锚点的 `region` 裁剪，写到 `docs/anchors/hsr/<state>/<anchor_id>.png`；
6. 重写 `docs/anchors/hsr/README.md` 的索引表（state / anchor / region / size / note）。

当前 `docs/anchors/hsr/` 覆盖三个界面、41 张裁剪图；`title_enter` 属于标题界面，不在脚本的三种状态里，表中标记为未捕获，需要时手工截图标定。**改过 `region` 后必须重跑脚本**，并逐张打开 PNG 核对；证据图与 YAML 不一致时以证据图为准。

## 4. 手机 UI 的四列网格规律

星铁手机主界面（`Esc` 打开）是 **4 列 × 6 行**网格，实测归一化中心：

- 列中心 `x ≈ 0.683 / 0.744 / 0.805 / 0.866`，列步长约 **0.061**；
- 行中心 `y ≈ 0.298 / 0.412 / 0.527 / 0.641 / 0.755 / 0.870`，行步长约 **0.114–0.115**；
- 每个格子的矩形约为 **0.052 × 0.068**，即 `region = [cx-0.026, cy-0.034, cx+0.026, cy+0.034]`。

对应到 `configs/hsr.yaml` 的 22 个图标：

| 行 \ 列 | 第 1 列 (0.683) | 第 2 列 (0.744) | 第 3 列 (0.805) | 第 4 列 (0.866) |
|---|---|---|---|---|
| y 0.298 | `phone_store` 商店 | `phone_friends` 好友 | `phone_commission` 委托 | `phone_achievement` 成就 |
| y 0.412 | `phone_diary` 旅情事记 | `phone_synthesis` 合成 | — | — |
| y 0.527 | `phone_mail` 短信 | `phone_honor` 无名勋礼 | `phone_warp` 跃迁 | `phone_role` 角色 |
| y 0.641 | `phone_guide` 指南 | `phone_multiplayer` 联机玩法 | `phone_nav` 导航 | `phone_tutorial` 教学目录 |
| y 0.755 | `phone_team` 编队 | `phone_backpack` 背包 | `phone_tasks` 任务 | `phone_tools` 游戏工具 |
| y 0.870 | `phone_feedback` 问题反馈 | `phone_knowledge` 智库 | `phone_bookshelf` 书架 | `phone_hot` 版本热点 |

补充：

- 第 2 行实测只有两个图标（旅情事记、合成），其余两格为空，不要机械补满。
- 手机右上角关闭 X 单独校准为 `phone_close`：`[0.938, 0.012, 0.992, 0.062]`；部分子面板复用同一位置。
- 手机菜单用 `Esc` 开/关；右上角一排最左侧的 `hud_phone` 实测点不开手机，别拿它当入口。
- 网格规律来自 2560×1600、DPI 120% 的实机。换宽高比或大版本后，先抽 2–3 个点复核；不要跨游戏直接复用。

## 5. 常见坑

| 症状 | 原因 | 处理 |
|---|---|---|
| 启动后点击无效，一直停在标题 | 启动 splash 期间输入被吞；`wait stable 800ms` 不能判断标题已加载 | `enter_game` 改为固定 **等 42 s → 点 `title_enter` → 等 35 s**；别在 splash 上抢点 |
| UI 点击没反应 | Unity 需要先收到 hover 帧 | runtime 的 click 会先移动再停 **50 ms** 才按下；统一走 `game_act`，不要自己发裸点击 |
| 改完 yaml 仍报 `UNKNOWN_ANCHOR` | MCP 进程旧版本会缓存 profile | 现版本按 `configs/*.yaml` 的 mtime+size 指纹热加载（`Runtime._reload_profiles_if_changed`）；先看 `game_profiles.errors`，确认改的是被加载目录，必要时重启 DSH 重载 MCP |
| `GetWindowRect failed (error 1400)` / `WINDOW_NOT_FOCUSED` | 游戏重启后缓存 hwnd 失效（旧版本报 error 1400，现版本会先校验句柄并报 `WINDOW_NOT_FOCUSED`） | 重新 `game_focus`；runtime 会清掉失效缓存 |
| `WINDOW_NOT_FOREGROUND` | 别的窗口抢了前台 | 重新 `game_focus`，不要绕过前台校验 |
| 截图全黑 / 旧帧 / 被遮挡 | 窗口不在前台、锁屏、休眠，或全屏 D3D 走了窗口 DC | 确认 `foreground: true`、`backend: screen`，解锁/唤醒后重截；看 `notice` |
| 点击位置整体偏了 | `region` 写成了 `[x, y, w, h]` | 改回 `[x0, y0, x1, y1]`；用 `dry_run` 的 `normalized`/`screen` 核对 |
| 手机入口点不开手机 | 右上角最左图标不是手机，实测无反应 | 用 `Esc` 打开手机；该图标保留为 `hud_phone` 但不要当手机入口 |
| 终末地游戏内所有输入无效 | ACE 反作弊过滤 SendInput | 按合规底线不绕过；终末地只做「只读副驾」（截图 + 识别 + 提示） |
| 证据表里没有 `title_enter` | `anchor_snips.py` 只截 ingame/phone/map 三种状态 | 标题锚点手工截图核对，或扩展脚本状态机 |
| 游戏启动报「网络连接错误」 | 继承了死代理环境变量 | 按 §2.1 清 6 个代理变量后重启游戏 |
| profile 整个不见了 | YAML 解析失败，被记入 `game_profiles.errors` | 先修 YAML 缩进/格式；runtime 不会因单个 profile 崩溃 |

## 6. 安全红线

1. **`dry_run` 默认开启**。profile 里 `safety.dry_run: true`，任何真实点击都必须显式 `dry_run: false` 且一次只做一个动作。
2. **F12 急停**。runtime 监听 `safety.emergency_stop_key`（默认 F12），触发后拒绝后续输入；`game_stop` 会释放所有按住的键/鼠标并在下次重置急停状态。发现输入失控先 `game_stop`。
3. **前台校验不可绕过**。`input.focus_check: true` 时，每次注入前校验前台窗口；不在前台就报 `WINDOW_NOT_FOREGROUND`，不注入任何输入。不要通过改配置关掉它。
4. **只做合法 UI 操作**。只截图（GDI）和 `SendInput`；**不读游戏内存、不注入 DLL、不绕过反作弊**。星铁/终末地都有反作弊，出现弹窗、崩溃或异常立即停止该游戏。
5. **不做高风险动作**。抽卡、付费、删除、PvP 一律不做。profile 用 `confirm_before` / `allowed_tasks` / `disallow_pvp` 记录这些禁区；动作若带 `meta.confirm: true`，runtime 会直接拒绝（`CONFIRM_REQUIRED`），不交给模型判断。
6. **隐私**。只用测试账号；截图避免账号/UID 等隐私区域；`captures/` 已被 gitignore，入库的只有 `docs/anchors/` 下的裁剪证据图。

## 模板生成与 M1.0 定位（2026-11-08）

`game_locate` / `game_wait_for` 依赖每个锚点的 `template:` 图片。生成方式：

```powershell
$env:PYTHONPATH="C:\AI\anime-game-agent\src"
python scripts/build_templates.py hsr --write-config
```

- 脚本会依次把游戏置于 in-game / 手机 / 地图三态，各抓一张 1.0 帧，再按锚点 region 裁图，
  输出到 `assets/templates/hsr/<state>/<anchor_id>.png`，索引在 `assets/templates/hsr/index.json`。
- 只在特定画面存在的锚点（如 `title_enter`、地图页签）需要在对应画面下重新跑一次脚本才会补齐。
  缺模板的锚点仍可当坐标锚点使用（`game_act` 点击），但 `game_locate` 会返回 `TEMPLATE_MISSING`。
- `game_locate` 默认在锚点 region 外扩 1 倍的搜索框内匹配（快）；需要全屏搜索时显式传
  `region: [0, 0, 1, 1]`。命中分数低于锚点 `threshold` 时返回 `found: false`，不算错误。

## 感知等待与状态检查（M1.5）

技能里不要写死 `sleep`：把「等到某个界面出现」写成 `wait check`，由 profile 的 `checks:`
驱动（模板或 OCR），超时会抛 `CHECK_TIMEOUT`，并带上 `attempts` 与最后一次检查结果。

```yaml
checks:
  in_game: {anchor: hud_chat, present: true, threshold: 0.8}
  title_screen:
    ocr: {region: [0.40, 0.92, 0.62, 0.99], contains: 点击进入, preset: fast}

skills:
  - id: enter_game
    confirm: [in_game]
    actions:
      - {type: wait, condition: {kind: check, name: title_screen, timeout: 120, interval: 1.0}}
      - {type: click, target: {anchor: title_enter}, button: left, clicks: 1}
      - {type: wait, condition: {kind: check, name: in_game, timeout: 120, interval: 1.0}}
```

注意：
- `title_screen` 用 OCR 而不是模板：标题文字（「点击进入」）在不同分辨率/缩放下比图形模板稳。
- 冷启动时窗口可能在 splash、标题、加载之间停留很久，所以 timeout 给到 120 s；
  首帧 OCR 含引擎初始化，实际耗时可能超过预算（超时是下界）。
- 战斗/剧情等非自由行动场景 `in_game` 应为 false，技能守卫会拦住输入；这是期望行为。
