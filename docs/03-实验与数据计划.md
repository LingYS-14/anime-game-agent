## 1. M0 参考实验：GameScaling 零样本可用性（可选）

### 1.1 要回答的问题

> 在**没有**任何二游数据微调的情况下，GameScaling-2B-S3 能不能对终末地战斗画面，输出**格式合法、语义合理、可执行**的 200 ms 动作块？

这是原方案最大的技术不确定性。现在它**降为参考实验**：只花约 5 人日，不阻塞星铁 UI 与终末地地图/基建；即使全红，也不影响主路线。

### 1.2 假设与判定

- **H1**：合理动作率 ≥ 50% → 绿，L1 进入产品路径。
- **H2**：30%–50% → 黄，L1 只做研究支线，产品用脚本宏。
- **H3**：< 30% → 红，GameScaling 不进产品路径。

辅助门槛：解析成功率 ≥ 95%，格式有效率 ≥ 90%，p95 延迟 ≤ 700 ms。任一项不达标，即使合理动作率绿，也降一级。

### 1.3 材料

| 项 | 规格 |
|---|---|
| 游戏 | 原神（须弥/枫丹战斗）、绝区零（训练场/空洞战斗） |
| 片段 | 100 段 × 2 s，1080p30，H.264，无 UI 遮挡关键区域 |
| 采样 | 5 Hz（每 200 ms 一个决策点），共约 1000 个决策点 |
| 历史 | 5 帧（当前帧 + 前 4 帧，约 166 ms） |
| 提示词 | 官方模板 + 适配后的 GAME_RULES/KEY_BINDINGS（保留三个标题） |
| 模型 | 2B-S3 为主；0.8B-S3、9B-S3（云/4bit）做对照 |
| 硬件 | 4090 Laptop 16 GB，`gpu-memory-utilization 0.4`，`max-model-len 8192` |

**片段选择原则**

- 覆盖：普攻、重击、元素战技、元素爆发、闪避、切人、跑图、攀爬、下落攻击。
- 排除：菜单、对话、抽卡、加载、过场动画（这些不是 L1 的场景）。
- 每段开头保留 0.5 s 上下文，避免第一帧信息不足。

### 1.4 流程

1. **录制**：按 §2 的工具录 100 段；同时记录人工输入（作为"人类参考动作"）。
2. **离线推理**：对每个决策点 t，取帧 `[t-4..t]`，发给本地 vLLM，得到文本动作。
3. **解析**：用 `gamescaling.action.parse_action` 严格解析；失败转 lenient；记录错误类型。
4. **可视化**：把动作画在帧上（鼠标箭头 + 按键高亮 + 6 段分组），生成盲评视频。
5. **人工盲评**：每段抽 2 个决策点，共 200 个；评分者只看"帧 + 动作"，不看模型名。
   - 2 = 合理：方向/按键与画面意图一致，可直接执行。
   - 1 = 可接受：方向大致对，但有抖动/多余键/时机偏差。
   - 0 = 荒谬：反向、乱按、明显不可执行。
6. **对照**：同一批帧，用"人类参考动作"做上界；用"全 no-op"做下界。
7. **消融**（可选，各 200 点）：
   - 历史 0 / 2 / 5 帧；
   - reasoning on / off；
   - 0.8B / 2B / 9B；
   - 官方提示词 vs 二游适配提示词；
   - 1280×720 vs 1920×1080 输入。

### 1.5 指标

| 指标 | 定义 | 采集方式 |
|---|---|---|
| parse_rate | 成功解析 / 请求 | 客户端统计 |
| valid_rate | 解析后动作在键位/范围内可执行 / 请求 | 校验器 |
| sensible_rate | 评分 ≥ 1 / 盲评样本 | 人工 |
| exact_rate | 评分 = 2 / 盲评样本 | 人工 |
| noop_rate | 输出 no-op / 请求 | 解析器 |
| dropped_rate | 词表外 token 数 / 总 token | 解析器 |
| latency_p50/p95 | 请求 → 响应 | 客户端 |
| action_distance | 与人类动作的鼠标方向余弦/键位 Jaccard | 离线计算 |

### 1.6 判定与产出

```text
绿：sensible ≥ 50% 且 parse ≥ 95% 且 valid ≥ 90% 且 p95 ≤ 700ms
黄：sensible 30–50%，或辅助门槛有一项不达标
红：sensible < 30%
```

**产出**：`reports/M0-决胜实验.md`，包含：

- 数据表（按游戏/场景/模型分组的指标）；
- 20 个典型成功/失败案例（帧 + 动作 + 评分）；
- 失败模式 Top 5（反向、抖动、乱按、时机、无响应）；
- 结论与建议（绿/黄/红 + 下一步）。

### 1.7 成本与时间

| 项 | 估算 |
|---|---|
| 环境搭建（WSL2/vLLM/驱动） | 3–5 人日 |
| 录制 + 标注 | 3 人日 |
| 推理（1000 点 × 2B） | 约 0.2 s/点 → 200 s GPU，可忽略 |
| 人工盲评 200 点 | 4 h |
| 报告 | 1 人日 |
| **合计** | **约 10 人日 / 2 周**（其中环境占一半，是一次性成本） |

## 2. 录制工具规格

### 2.1 目标

一次录制，同时得到：**视频、输入事件、模型动作、游戏状态、时间戳**，且能逐帧对齐。它是数据飞轮的地基，不是附属品。

### 2.2 采集

| 通道 | 实现 | 频率 | 备注 |
|---|---|---|---|
| 画面 | Windows Graphics Capture | 30 fps | 只抓客户区；H.264 编码 |
| 键盘 | Raw Input（`WM_INPUT`）或低级钩子 | 事件级 | 记录 scan code + 时间戳 |
| 鼠标 | Raw Input | 事件级 | 相对位移、按键、滚轮 |
| 状态 | 感知管线输出 | 5–30 Hz | 屏幕/HP/体力/货币 |
| 动作 | 执行器日志 | 事件级 | 模型/脚本/人工，带 source |
| 时钟 | `time.perf_counter()` | — | 所有通道共用 |

**对齐**：视频用 CFR 30 fps，帧序号 `n` 对应 `t0 + n/30`；事件时间戳转成相对 `t0` 的秒。录制结束后做一次"拍手"校验（画面变化与按键事件同时发生），偏差 > 50 ms 则告警。

### 2.3 文件布局

```text
data/sessions/<session_id>/
├── meta.json          # 游戏、分辨率、窗口、profile 版本、操作者、备注
├── frames.mp4         # H.264, 30fps, yuv420p, faststart
├── frames.jsonl       # 每帧: {index, ts, pts}
├── events.jsonl       # 键鼠事件
├── actions.jsonl      # 模型/脚本动作
├── states.jsonl       # 感知状态
└── thumbs/            # 可选：每 5 s 一张缩略图
```

### 2.4 数据 schema

**meta.json**

```json
{
  "session_id": "20261108-153012-genshin",
  "game": "genshin",
  "profile_version": "0.1.0",
  "resolution": [1920, 1080],
  "window_rect": [0, 0, 1920, 1080],
  "dpi_scale": 1.0,
  "fps": 30,
  "started_at": "2026-11-08T15:30:12+08:00",
  "operator": "A",
  "notes": "须弥沙漠战斗，队伍固定"
}
```

**events.jsonl**

```jsonl
{"ts": 12.345, "type": "key_down", "key": "W", "scan": 17}
{"ts": 12.678, "type": "mouse_move", "dx": 14, "dy": -3}
{"ts": 12.700, "type": "mouse_down", "button": "left"}
{"ts": 12.900, "type": "wheel", "delta": 1}
```

**actions.jsonl**

```jsonl
{"ts": 12.800, "source": "reflex", "chunk": {"x": 12, "y": -3, "z": 0, "groups": [["W"], ["W"], [], [], [], []]}, "raw": "<|action_start|>..."}
```

**states.jsonl**

```jsonl
{"ts": 12.833, "screen": "combat", "hp": 0.82, "energy": 0.41, "stamina": 120, "party": ["A","B","C","D"]}
```

### 2.5 编码与存储

- 视频：H.264，CRF 20–23，`yuv420p`，`+faststart`；不录音频。
- 文件切分：每 10 分钟一个 mp4，避免单文件过大。
- 隐私：录制前按 profile 的 `privacy_regions` 模糊 UID/昵称/好友列表；默认本地存储，不上传。
- 校验：录制结束算 SHA256，写入 meta；损坏文件隔离。

## 3. 200 ms 动作块构建

### 3.1 定义

GameScaling 的动作是 200 ms 一块，内部 6 个 33.33 ms 子步：

```text
X Y Z ; g1 ; g2 ; g3 ; g4 ; g5 ; g6
```

- `X, Y`：整个 200 ms 的鼠标位移，单位千分之一屏宽；`X = Σdx / width × 1000`，clamp ±1000；`X>0` 右，`Y>0` 下。
- `Z`：滚轮档位，clamp ±5。
- `g1..g6`：每个子步按住的键，最多 4 个；空组表示该子步不按键。
- 文本包在 `<|action_start|> ... <|action_end|>` 中；只取最后一个 `</think>` 之后的内容。

### 3.2 从人工输入构建标签

```python
def build_chunk(events, t0, width, fps=30):
    window = [e for e in events if t0 <= e.ts < t0 + 0.2]
    dx = sum(e.dx for e in window if e.type == "mouse_move")
    dy = sum(e.dy for e in window if e.type == "mouse_move")
    x = clamp(round(dx / width * 1000), -1000, 1000)
    y = clamp(round(dy / width * 1000), -1000, 1000)
    z = clamp(dominant_wheel(window), -5, 5)

    groups = []
    for i in range(6):
        a, b = t0 + i * 0.03333, t0 + (i + 1) * 0.03333
        keys = held_keys(window, a, b)          # 该子步内处于按下状态的键
        keys = sorted(keys)[:4]                  # 最多 4 个
        groups.append(keys)

    return Action(x=x, y=y, z=z, groups=groups)
```

**细节**

- `held_keys` 用"区间重叠"判断：按键按下时间 < 子步结束 且 抬起时间 > 子步开始。
- 鼠标位移按整个 200 ms 聚合，不再拆到子步（与官方格式一致）。
- 空组保留分号；解析器要求 6 组。
- 人工输入的抖动/连点要保留（这是真实行为），但要做异常过滤：单帧 > 2000 千分位视为瞬移，丢弃。

### 3.3 样本组织

```json
{
  "session_id": "...",
  "t": 12.8,
  "images": ["frames/000384.jpg", "frames/000385.jpg", "frames/000386.jpg", "frames/000387.jpg", "frames/000388.jpg"],
  "system": "<完整系统提示词>",
  "answer": "<|action_start|>12 -3 0 ; W ; W ; ; ; ; <|action_end|>",
  "meta": {"game": "genshin", "screen": "combat", "source": "human"}
}
```

- 历史 5 帧：当前帧 + 前 4 帧（30 fps 下约 133 ms）。
- 划分：**按 session 划分**训练/验证/测试（70/15/15），绝不按帧随机划分，否则同一场战斗的相邻帧泄漏。
- 平衡：静止/无输入样本占 20–30%，不要全删（否则模型永远在动）；战斗/跑图/技能按场景分层采样。

### 3.4 数据量与存储估算

| 项 | 规格 | 估算 |
|---|---|---|
| 原始视频 1080p30 | H.264 CRF 20，4–6 Mbps | 1.8–2.7 GB/h；30 h ≈ 54–81 GB |
| 原始视频 720p30 | 2–3 Mbps | 0.9–1.35 GB/h；30 h ≈ 27–40 GB |
| 5 Hz 帧（30 h） | 54 万帧 | 不落 PNG；训练时从视频解码 |
| 若缓存 720p JPEG | ~60–80 KB/帧 | 32–43 GB |
| 事件/状态 JSONL | 1–5 MB/h | < 1 GB |
| SFT 样本 20–50k | 每样本 1–5 图 | 图像缓存约 1.2–3 GB |
| **建议 SSD** | 2 TB NVMe | 视频 + 缓存 + 模型权重够用 |

> 省空间策略：只保留"有动作"的片段 + 每 10 分钟 10 s 静止片段；原始视频定期归档到机械盘。

## 4. SFT 计划（v0.3 不启动，保留为未来模板）

> v0.3 已确认不做 SFT；本节只在“战斗参考实验”出现黄/绿且未来决定投入时启用。

### 4.1 目标

用自采的二游战斗数据，把 2B-S3 的"合理动作率"从零样本基线提升 ≥ 15 个百分点，或战斗胜率 +10%。

### 4.2 基座与框架

| 项 | 选择 | 备注 |
|---|---|---|
| 基座 | `THUSI-Lab/GameScaling-2B-S3` | 已在二游邻近域 CPT；比 Qwen 基座更接近目标 |
| 备选 | 9B-S3（云） | 质量上限更高，成本高 |
| 框架 | ms-swift（首选）/ LLaMA-Factory | 需确认 Qwen3.5-VL 支持；否则 transformers + TRL |
| 精度 | bf16（LoRA）/ 4-bit QLoRA（16 GB） | 2B LoRA 在 16 GB 上需 4-bit + 梯度检查点，且可能要降到 1 图/样本；跑不动就上云 24 GB |
| 模板 | checkpoint 自带 `chat_template` | 不要手写；保持与推理一致 |

### 4.3 数据配比

| 来源 | 比例 | 说明 |
|---|---|---|
| 自采原神战斗 | 50% | 含普攻/技能/闪避/切人 |
| 自采绝区零战斗 | 30% | 高速动作，补时序 |
| 自采跑图/采集 | 10% | 导航/视角 |
| 公开 GameScaling 示例/其他 | 10% | 防遗忘，保持格式 |

- 总量：20–50k 样本（约 10–25 h 有效动作）。
- 过滤：解析失败、动作全空、画面遮挡、加载/过场，全部剔除。
- 标签：assistant-only loss；user 侧图像与提示词不计 loss。

### 4.4 超参（起点）

```yaml
lora: {r: 32, alpha: 64, dropout: 0.05, target: all_linear}
lr: 1.0e-4
epochs: 1-2
batch_size: 1
grad_accum: 16
max_length: 4096
image_resolution: [1280, 720]
warmup_ratio: 0.03
bf16: true
gradient_checkpointing: true
```

### 4.5 评测

- 留出 session：合理动作率、exact rate、动作距离、no-op 率。
- 闭环：3 个战斗场景 × 20 次，胜率/存活/耗时/接管次数。
- 对照：零样本 2B-S3、SFT 2B-S3、脚本宏、9B-S3（云）。
- 显著性：Wilson CI；SFT vs 零样本用同场景配对比较。

### 4.6 风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 过拟合单游戏 | 原神涨、ZZZ 跌 | 混采、按游戏分层、留出跨游戏测试 |
| 灾难性遗忘 | 通用指令能力下降 | 混 10% 通用/示例数据；只调 LoRA |
| 动作不平衡 | 只会普攻 | 按动作类型重采样；类别权重 |
| 图像-文本错位 | 看得懂但按错 | 检查时间对齐；用"拍手"校验 |
| 许可 | GameScaling research-only | 不商用；发布只发 LoRA/脚本，不发基座 |

## 5. 闭环评测协议

### 5.1 单任务评测

1. **准备**：测试账号；关闭无关程序；固定分辨率/画质/网络；记录游戏版本。
2. **重置**：回到主界面；检查体力/货币/任务进度；必要时重启游戏。
3. **开始**：调用 `kiseki run --task <id> --max-seconds <T>`。
4. **成功判定**：优先用状态字段（体力减少、奖励领取标志、任务进度），其次 OCR，最后人工看回放。
5. **失败分类**：感知错 / 技能错 / 规划错 / 游戏异常 / 环境异常 / 未知。
6. **记录**：耗时、干预次数、API 成本、截图、日志、视频。
7. **重复** N=20；换时段再跑一轮，避免日常刷新偏差。

### 5.2 成功判定示例

| 任务 | 成功条件 | 超时 |
|---|---|---|
| 领取邮件 | 邮件红点为 0 且回到主界面 | 90 s |
| 每日签到 | 签到按钮变为"已签到" | 60 s |
| 清体力（花萼） | 体力减少 ≥ 10 × count 且结算屏出现 | 8 min |
| 委托 | 4 个委托全部显示"已完成" | 10 min |
| 模拟宇宙（简化） | 通关第 1 层并领取 | 15 min |
| 战斗（L1） | 胜利且未阵亡且耗时 < 基线 × 1.2 | 5 min |

### 5.3 统计

- 成功率 + Wilson 95% CI。
- 每任务单独报告，不只看总数（防止"3 个简单任务拉高平均"）。
- 失败 Top 3 + 截图；每周对比上一周。
- 发布门槛：N=50，整体 ≥ 85%，且**每个任务** ≥ 70%。

### 5.4 评测环境

- 同一台机器、同一账号、同一网络；记录 GPU 温度/频率（笔记本降频会影响延迟）。
- 游戏画质固定（避免模板失配）；UI 缩放固定。
- 评测时关闭录屏以外的后台程序；录屏本身用 GPU 编码，避免抢 CPU。

| 5 | 写 `configs/hsr.yaml` 的邮件流程 | 主界面 → 邮件 → 领取 → 返回，锚点/OCR 区域齐全 |
| 6 | 跑 5 次邮件任务 | 5/5 成功；记录失败原因与耗时 |
| 7 | 终末地跑图截 30 张小地图，标 10 个 waypoint | 瓦片可拼接，waypoint 有坐标与朝向 |

> 第一周不装 WSL、不拉 vLLM、不训模型。先把“DSH 能看见、能点、能停”跑通。

## 8. 终末地地图实验协议（v0.3）

### 8.1 目标与边界

证明“小地图定位 + 拓扑导航”在终末地可行，不做完整 SLAM、不做多层、不做全自动探索。先单层、固定 5 条路线。

### 8.2 数据采集

- 自己跑图，截 30–50 张小地图/地图界面；分辨率与游戏设置固定（1080p、默认 UI 缩放）。
- 拼 2D 瓦片（OpenCV Stitcher 或手工对齐）；保存 `map.png` 与缩放/偏移元数据。
- 标 20–30 个 waypoint：传送点、路口、资源点、基建入口；字段 `id/x/y/heading/neighbors/type`。
- 每条路线人工走一遍，记录人类耗时作为基线。

### 8.3 定位管线

1. 以 10 Hz 裁小地图区域（profile 给归一化 bbox）。
2. ORB/SIFT 特征 + 单应性匹配到瓦片；低纹理时用模板块 + 前一帧光流兜底。
3. 玩家箭头模板多角度匹配得到 heading；输出 `x/y/heading/confidence`。
4. 置信度 <0.6 暂停并请求重定位；连续 3 次失败交还用户。
5. 偏航 >2 m 或卡住 >3 s 触发重定位；卡住 >5 s 判定该次失败。

### 8.4 指标与判定

| 指标 | 目标 |
|---|---|
| 单帧定位成功率 | ≥95%（100 帧） |
| 位置误差 | ≤2 m（或小地图 3 px） |
| 朝向误差 | ≤10° |
| 路线成功率 | 5 条 ×4 次 = 20 次，≥16 次（80%） |
| 用时 | ≤2× 人类基线 |
| 卡住 | 单次 >5 s 即失败 |

### 8.5 失败分类

低纹理/大色块、遮挡、小地图旋转、楼层错位、UI 弹窗遮挡、waypoint 拓扑缺失。每周统计 Top 3，决定是补特征、补 waypoint 还是改路线。

## 9. 终末地基建实验协议（v0.3）

### 9.1 目标与边界

从零建**一条**产线（2 采集 → 1 加工 → 1 输出），验证“读状态 → 规划 → 放置 → 监控 → 纠错”闭环；不做全自动基地、不做多产线优化。

### 9.2 知识准备

- `recipes.yaml`：10–20 条配方，字段 `id/inputs/outputs/building/time/power/water/footprint/ports`。
- 建筑目录：先 4–5 种（采集、加工、输出、电力、物流）。
- 约束：网格尺寸、占地、朝向、连接口、电力/水源覆盖。

### 9.3 管线

1. 进基建总览，OCR + 模板抽 `buildings[]`、`inventory`、`power`、`water`、`logistics`。
2. DSH 读状态 + 配方图，给出产线草案（建筑数量/位置/连接）。
3. 约束检查器验证网格、占地、连接、电力、物流；不通过则重排。
4. runtime 执行：相机对准 → 建造菜单 → 放置/旋转/连接；每步截图校验。
5. 监控 5 分钟：产量、堵塞、缺电/缺水；异常时 DSH 解释并重规划。
6. 失败回滚：拆除本次放置或读档；记录回滚原因。

### 9.4 指标与判定

| 指标 | 目标 |
|---|---|
| 建线时间 | ≤30 分钟 |
| 产率 | 目标值 ±20% |
| 连续无堵塞 | ≥5 分钟 |
| 电力裕度 | ≥10% |
| 人工干预 | ≤2 次 |
| 放置成功率 | ≥90% |
| 回滚成功率 | 100% |

10 次从干净存档开始，≥8 次通过为 go。

### 9.5 失败分类

点偏/网格没吸附、朝向错、连接口没接上、配方选错、缺电/缺水、物流堵塞、状态识别错。按类统计，优先修“状态识别错”和“连接口没接上”——这两类最影响可信度。
